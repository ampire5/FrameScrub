# Fast image upscaling and Remaster standalone probes

2026-11-07, M4 Max, 36 GB, macOS27.2. Standalone experiment; no product integration,
model weights or Python runtime added to FrameScrub. The requested image task is
3840×2160 → 7680×4320 in about one second. Video restoration remains native4K.

## Sources and reproducibility

- PULSE/PULSE Fast2x: https://huggingface.co/Phips/PULSE
- SPAN Fast2x weights: https://github.com/Phhofm/models/releases/tag/2xBHI_small_span_fast_pretrain
- Exact SPAN architecture linked by that release: neosr-project/neosr commit
  `5d7a9ee658b26ea441859e25b942e266068950b0`, `neosr/archs/span_arch.py`.
- Remaster student: https://huggingface.co/seantempesta/remaster-drunet
- Remaster's UNetRes/basicblock implementation: https://github.com/cszn/KAIR

Python3.9, torch2.8.0, coremltools9.0, safetensors0.7, Pillow11.3, NumPy2.0.2.
Coremltools warns that torch2.8 is newer than its tested2.7; backend output parity checked.
All state dictionaries loaded strictly. PULSE imports of training registries removed and
ICNR initialization stubbed: learned initialization is entirely overwritten by strict loading;
the nonpersistent MKS base is generated by the original implementation. Actual2x parameter
counts are151,788 (Fast),338,268 (regular), rather than the card's4x counts.
SPAN's Python3.10 union in isinstance was replaced by a tuple for Python3.9. Its Conv3XC
branches were reparameterized once using the author's update_params, then replaced by the
resulting eval_conv; no per-frame weight fusion. Remaster uses3-channel RGB, UNetRes
nc=[16,32,64,128], nb=2, act_mode=R, bias=False, matching the author's instructions.

Apple's public FRC.mov frame90 at3s provides the native4K SDR input. Upscale samples use
that frame before additional compression; there is no8K ground truth. This is one moving
video frame, not evidence of quality across all photographs, text, illustrations or HDR.
Remaster uses matching H.264 QP42/QP32 and HEVC QP38 re-encodes (libx264 veryfast,
libx265 fast, yuv420p, two worker threads). HEVC additionally tested at1920×1080.

Scripts, exact weights/checksums, environment, raw logs, full images and comparison crops
are in the external research workspace. Experiments run sequentially,
CPU intra-op2/inter-op1; MPS memory limited to30% of its recommended device working set
(the runtime reports8.42GiB). Conversion/compilation and PNG encoding excluded from inference.
No private media used and no public repository assets added.

## Full4K input, Core ML FP16

Direct torchscript→MLProgram conversion, fixed1×3×2160×3840, macOS15 minimum target.
Device selection is significant: ALL was slower than explicit CPU_AND_GPU on this machine.
Labels describe allowed compute units, not proven per-operation device placement.

| Model | Output | CPU+GPU first predict / warm median, seconds | ALL subsequent predicts, seconds |
|---|---|---|---|
| PULSE Fast2x | 7680×4320 | .635 / .269 | .715, .694 |
| PULSE2x | 7680×4320 | .982 / .620 | 1.160,1.152 |
| SPAN Fast2x | 7680×4320 | .607 / .307 | 1.406,1.381 |
| Remaster student | 3840×2160 | .513 / .125 | .543,.475 |

Warm medians use three repeats following the first predict in a fresh process. Prior model/
driver caches may be warm: first-predict numbers are not a first-ever installation/compile
benchmark. Remaster CPU+NE subsequently.181,.168,.173s; no advantage over CPU+GPU here.

For still-image response, a separate pass includes PNG decode, float input preparation,
Core ML CPU+GPU prediction and creation of a native8K RGB8 image in memory:

| Model | First pass, seconds | Two following passes, seconds |
|---|---:|---|
| PULSE Fast | .739 | .604,.563 |

## Metal/MPS and bounded tiling

Whole-image MPS FP16: PULSE Fast.267/.270s after.591s first; PULSE.623/.623s after.793s
first; Remaster.131/.130s after.539s first. Readback measured separately.032/.013/.006s.
Driver-allocated memory after the pass was4.05/5.09/2.38GB respectively; this includes cached
GPU heaps and is not a precisely sampled peak live-tensor measurement.

SPAN whole-image MPS hit the configured8.42GiB cap and was stopped by the runtime. The
limit was not raised. Sequential tiles with64px real context produced the full8K image:

| SPAN input core | Tiles | First / next two seconds | Driver allocated after pass |
|---|---:|---|---|
| 1024 | 12 | .954 / .467,.467 | 7.54GB |
| 512 | 40 | .609 / .561,.562 | 3.24GB |

These tiled times include dispatch/copy into the resident output tensor; one tile in flight.
Smaller tiles trade extra overlap/work for bounded memory. SPAN tiled512 versus full Core ML
RGB8 MAE=.0245/255, P99=1. No obvious seams in inspected comparisons. This does not establish
that all tile sizes/content are artifact-free. Core ML CPU+GPU full-image is the preferable
measured native route here; MPS provides an independent parity and performance reference.

## Quality

Upscalers: modest differences from Lanczos on inspected native8K face/fur crops; no dramatic
detail invention like the earlier DeH264 sample. PULSE clean pretrains do not promise
compression cleanup. A one-second response is feasible for these weights on this Mac, but
cross-image quality and slower-device validation are still required before another app ships
them. PULSE Fast and SPAN Fast deserve the first broader image comparison; regular PULSE is
also near the requested budget with less timing margin.

Remaster: on H.264 QP42, QP32 and HEVC QP38 it mostly sharpens; obvious compression structures
remain. A fine checkerboard is introduced in smooth sky. It persists in FP32 and FP16 on a
matched HEVC crop with128px context: FP32/FP16 float RGB MAE=.0343/255, max=.1735/255,
both finite. This rules out FP16 as the cause in that comparison. Full4K Metal/CoreML RGB8
MAE=.1039/255, P99=1, so the quality problem also is not unique to the Core ML export.
H.264 QP42 face/fur RGB PSNR versus pre-reencode reference changes28.84→27.79 and
27.68→27.52dB; PSNR alone is not a perceptual quality judgment. The card documents targets
generated by SCUNet GAN plus unsharp masking, rather than an uncompressed capture reference.

Remaster MPS warm4K HEVC/H.264~.130s;1080p HEVC~.032s. Even the best full4K Core ML
measurement (.125s, about8fps before decode/display) does not meet30fps. Selected-region
inference could reduce work, but a detector/blending pipeline was not implemented: current
weights first fail the inspected quality criterion. A quality mask applied after whole-frame
inference would not save the inference work. A lightweight trained1x cleaner with actual
region selection remains a separate experiment, not a demonstrated solution.

## Verification

All reported successful runs returned finite output at expected native dimensions. CoreML
versus MPS RGB8 MAE PULSE Fast=.0339/255, PULSE=.0443/255, P99=1 for both. Full output PNGs
and comparison PNGs decoded successfully. Scripts, numerical results and weights remain outside
the repository. No product behavior changed; no product test rerun is required for these docs.
