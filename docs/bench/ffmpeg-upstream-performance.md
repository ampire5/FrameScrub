# FFmpeg 9.1 и master для FrameScrub

Проверено 20 ноября 2026 года. Последний стабильный выпуск — **9.1 Gauss**, опубликован 20 ноября. Сравнение исходников сделано между `n9.0.2`, `n9.1` (`74e43935`) и `master` (`7ddf7bc8`). Числа из коммитов относятся к тестам авторов. [Релизы FFmpeg](https://ffmpeg.org/download.html) · [тег n9.1](https://github.com/FFmpeg/FFmpeg/tree/n9.1) · [снимок master](https://github.com/FFmpeg/FFmpeg/tree/7ddf7bc8a482cf28b4fab2e63b7093ba35cb6a80)

## Обновление Edge за 23 ноября 2026 года

Рецепт сборки закрепляет `master-05c674c9132e` и выводит этот идентификатор через `av_version_info()`. Между предыдущим снимком и новым 91 коммит. Версия dav1d в рецепте та же, 1.5.5. [Сравнение FFmpeg](https://github.com/FFmpeg/FFmpeg/compare/7ddf7bc8a482cf28b4fab2e63b7093ba35cb6a80...05c674c9132eb13e65e3fb6e9b4cf1cad1219fd5) · [Рецепт сборки](../../scripts/build-deps.sh)

- MOV теперь предпочитает длительность из таблицы сэмплов `stts` значению `mdhd`. Это важно для проверки длительности и последнего кадра на MP4/MOV с противоречивыми заголовками. [Изменение MOV](https://github.com/FFmpeg/FFmpeg/commit/166b8be61863)
- Новый порядок программного декодирования HEVC касается кадров, где тайл разделён на несколько слайсов. На прямом пути VideoToolbox декодирование выполняет системный VideoToolbox. [Изменение HEVC](https://github.com/FFmpeg/FFmpeg/commit/f924d7b2ed30) · [VTBackend](../../Sources/FrameScrubCore/VTBackend.swift)
- В HTTP исправлено освобождение памяти после неудачного повторного подключения через прокси. Это важно для стабильности при сбоях соединения. [Изменение HTTP](https://github.com/FFmpeg/FFmpeg/commit/05c674c9132eb13e65e3fb6e9b4cf1cad1219fd5)

Статические библиотеки собраны для arm64 и x86_64. Вызов `av_version_info()` вернул новый идентификатор при нативном запуске и под Rosetta. Штатный набор тестов FrameScrub на arm64 прошёл, включая переходы и отмену чтения HLS. В отдельном прогоне `PerformanceTests` на M4 Max обратная прокрутка дала 589/589 попаданий для H.264 1080p и 357/357 для HEVC 4K HLG, без неверных кадров. p99 до получения правильного кадра из прогретого кэша составил 0,02 мс в обоих случаях. Это замер кэша во время кросс-сборки, без A/B для холодных переходов и без замера физического показа кадра.

## Что проверить по release notes 9.1

Файл `RELEASE_NOTES` отсылает к `Changelog` и истории коммитов. Из объявленных возможностей к текущему плееру ближе всего новый транспорт `libcurl` для HLS и пакетный фильтр `trim` для экспорта без перекодирования. [Release notes](https://github.com/FFmpeg/FFmpeg/blob/n9.1/RELEASE_NOTES) · [Changelog](https://github.com/FFmpeg/FFmpeg/blob/n9.1/Changelog)

- **Пакетный `trim`.** Умеет задавать границы по PTS/DTS и обрезать звук с точностью до сэмпла через packet side data. Стоит проверить на аудиограницах экспортируемых клипов. Для видео `preroll` оставляет опорные пакеты в ремаксе, а граница по PTS может убрать ссылку, нужную последним B-кадрам. `ClipWriter` также сшивает несколько диапазонов и рассчитывает их общую временную шкалу. [Документация `trim`](https://ffmpeg.org/ffmpeg-bitstream-filters.html#trim) · [ClipWriter](../../Sources/FrameScrubCore/ClipWriter.swift)
- **AAC seek preroll.** Декодер может сообщать требуемый preroll в сэмплах через `AVCodecContext.seek_preroll`. FrameScrub сейчас запрашивает фиксированные 100 мс до нужной позиции и сам подрезает результат. Вариант для проверки точности старта аудио и объёма чтения на AAC-LC, HE-AAC и xHE-AAC, особенно после перехода через границу HLS-сегмента. [Изменения API 9.1](https://github.com/FFmpeg/FFmpeg/blob/n9.1/doc/APIchanges#L4-L12) · [AudioDecoder](../../Sources/FrameScrubCore/AudioDecoder.swift)

## Что даёт 9.1 без изменения плеера

- **Программный HEVC.** Новый NEON-код для SAO edge 10/12 бит ускоряет соответствующее ядро на AArch64, а ранний выход из расчёта силы деблокинга дал автору до 3% на однопоточном 4K inter decode. Параллельное декодирование тайлов применимо к HEVC с одним слайсом на кадр, разбитым на независимые тайлы, при slice threading. Заявленные для этого случая 2,3× в среднем измерены на восьми потоках. FFmpeg обычно предпочитает frame threading, если кодек его поддерживает. Сравнить штатный выбор с явным slice threading на Main10 software fallback при одинаковом ограничении потоков, учитывая буферизацию кадров при frame threading. [NEON SAO](https://github.com/FFmpeg/FFmpeg/commit/b37f0894) · [деблокинг](https://github.com/FFmpeg/FFmpeg/commit/05c6ee22) · [тайлы](https://github.com/FFmpeg/FFmpeg/commit/fc3ff773) · [выбор режима потоков](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libavcodec/pthread.c#L44-L63)
- **HLS VOD и MP4.** HLS уточняет временную отметку начала сегмента по пакетам и сохраняет первый ключевой кадр при переходе на границу сегмента. Есть исправление HTTP byte-range сегментов. MOV ускоряет поиск позиции в таблице сэмплов для больших edit lists с composition offsets. Это повод повторить проверки переходов на границе сегмента, между раздельными A/V-дорожками, по byte ranges и по MP4 с edit list и B-кадрами. [Начало HLS](https://github.com/FFmpeg/FFmpeg/commit/f6fa0d3f) · [HLS seek](https://github.com/FFmpeg/FFmpeg/commit/848fb754) · [HLS byte ranges](https://github.com/FFmpeg/FFmpeg/commit/d9242028) · [MOV edit lists](https://github.com/FFmpeg/FFmpeg/commit/9181f3a9)
- **Другие декодеры.** Для H.264 добавлена поддержка data partitioning, для VP9 исправлен флаг discard у `show_existing_frame`. Это изменения совместимости и корректности выдачи кадров. Обёртка `libdav1d` и реализация VideoToolbox в проверенных исходниках одинаковы в 9.0.2 и 9.1. Версия dav1d 1.5.4 уже была закреплена в FrameScrub. Её ускорения 8-битного intra prediction на AArch64 и планирования тайлов относятся к dav1d. [Changelog 9.1](https://github.com/FFmpeg/FFmpeg/blob/n9.1/Changelog) · [VP9](https://github.com/FFmpeg/FFmpeg/commit/8b3525e7) · [dav1d 1.5.4 NEWS](https://github.com/videolan/dav1d/blob/1.5.4/NEWS) · [сборка FrameScrub](../../scripts/build-deps.sh)
- **Прямой VideoToolbox.** Для H.264/HEVC с подходящим avcC/hvcC прямой путь уже держит до четырёх асинхронных запросов и выдаёт NV12/P010 либо поддерживаемый lossless packed 10-bit. В обёртке FFmpeg остаётся ожидание после отправки каждого кадра. На прямом пути область влияния обновления — демультиплексор, пакеты и их время. На аппаратном fallback FrameScrub уже забирает `CVPixelBuffer` из `AVFrame`, поэтому новый `av_hwframe_get_transfer_buffer()` к этому пути не применяется. [VTBackend](../../Sources/FrameScrubCore/VTBackend.swift) · [FFmpegBackend](../../Sources/FrameScrubCore/FFmpegBackend.swift) · [upstream VideoToolbox](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libavcodec/videotoolbox.c#L746-L771) · [API буфера передачи](https://github.com/FFmpeg/FFmpeg/commit/b8249f73a7c)

## Что имеет смысл измерить отдельно

| Кандидат | Где может помочь и что проверить |
|---|---|
| **libcurl для HLS VOD** | В 9.1 появился опциональный транспорт с общим циклом и пулом соединений на `AVFormatContext`, HTTP/2 и HTTP/3 зависят от сборки curl и сервера. Для отдельной сборки нужны `--enable-libcurl`, libcurl ≥ 7.88.0 и явный выбор `prefer_libcurl`. Текущий `io_open` вызывает публичный `avio_open2`, который передаёт NULL вместо владельца, поэтому каждое открытие получит отдельный цикл. Для опыта сохранить исходный callback FFmpeg и делегировать ему открытие после установки опций. У видео и аудио всё равно отдельные контексты. Текущий HLS отключает `http_multiple`, а libavformat отключает нативный keep-alive при custom `io_open`. Проверить TLS дочерних URL, таймауты открытия и чтения, отмену, диапазоны, число запросов и память с учётом буфера curl по умолчанию 4 МиБ на вход. Сравнить p95 холодного перехода при одинаковом RTT и ограничении параллелизма. [Документация протокола](https://ffmpeg.org/ffmpeg-protocols.html#libcurl) · [владелец цикла](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libavformat/libcurl.c#L1091-L1113) · [стандартный callback](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libavformat/options.c#L141-L158) · [avio_open2](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libavformat/avio.c#L536-L570) · [нативный keep-alive](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libavformat/hls.c#L2490-L2503) · [MediaSource](../../Sources/FrameScrubCore/MediaSource.swift) |
| **AV1 software, `max_frame_delay=1`** | В существующей обёртке глубину буферизации кадров можно ограничить независимо от числа рабочих потоков. Сравнить задержку первого точного кадра после flush с устойчивой скоростью воспроизведения и загрузкой CPU. `skip_frame` обёртка dav1d читает при открытии, поэтому запись `AVDISCARD_NONREF` на каждом пакете не переключает для неё режим покадрово. [Обёртка libdav1d](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libavcodec/libdav1d.c#L205-L260) · [FFmpegBackend](../../Sources/FrameScrubCore/FFmpegBackend.swift) |
| **Экспериментальный libswscale** | `SWS_UNSTABLE` и AArch64/x86 SIMD-бэкенды уже существовали в 9.0.2. Они доступны через динамический `sws_scale_frame`. Нынешний shim использует `sws_scale` и legacy backend. Измерить только software-конверсию planar → CVPixelBuffer NV12/P010 с фактическими stride и отдельно проверить значения пикселей, диапазон, цветность и HDR. Пометка upstream допускает иной результат и меньшую скорость. [Контракт swscale](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libswscale/swscale.h#L109-L185) · [выбор бэкенда](https://github.com/FFmpeg/FFmpeg/blob/n9.1/libswscale/swscale.h#L300-L312) · [SoftwareFrameConverter](../../Sources/FrameScrubCore/SoftwareFrameConverter.swift) · [shim](../../Sources/CFFmpeg/shim.h) |
| **Декодирование только метаданных H.264/HEVC** | 9.1 реализует `skip_pred=ALL` вместе с `skip_idct=ALL` для метаданных кадров с неопределёнными пикселями. Возможный эксперимент для источников, где пакетного индекса недостаточно. Текущий локальный индекс уже строится по пакетам. Видимый кадр и его опорные кадры для точного перехода требуют обычной реконструкции. Экспериментальный граф BSF также обрабатывает пакеты и сам по себе доступ к произвольному декодированному кадру не даёт. [H.264](https://github.com/FFmpeg/FFmpeg/commit/51903077) · [HEVC](https://github.com/FFmpeg/FFmpeg/commit/68fdc7b9) · [BSF API](https://github.com/FFmpeg/FFmpeg/commit/32a256f619a) · [MediaSource](../../Sources/FrameScrubCore/MediaSource.swift) |

## Локальные замеры на M4 Max

macOS 27.2.1, arm64, статические сборки FrameScrub. Для libswscale измерялось только преобразование одного синтетического кадра в заранее выделенный буфер в одном потоке. Оба формата 4:2:0, ограниченный диапазон BT.709, без изменения размеров. На каждый вариант семь серий по 40 преобразований с прогретым контекстом, порядок вариантов менялся. Активные пиксели в этом тесте совпали. У `SWS_UNSTABLE` выигрыша не обнаружено. Замер исключает декодирование, Core Video и отображение.

В [тестовом AV1 1080p](../../Tests/FrameScrubCoreTests/Fixtures.swift) после `avformat_seek_file` и `avcodec_flush_buffers` посчитано число видеопакетов до каждого из шести точных PTS. При четырёх потоках значения с автоматической задержкой составили 2/15/50/2/27/50. С `max_frame_delay=1` понадобилось 1/13/48/1/25/48 пакетов. При одном потоке эти же значения получились с обоими режимами. 9.0.2 и 9.1 с dav1d 1.5.4 дали одинаковые результаты. Замер считает пакеты. Для решения о настройке нужны задержка и пропускная способность на разных AV1-файлах.

В [штатном тесте обратной прокрутки](../../Tests/FrameScrubCoreTests/PerformanceTests.swift) FFmpeg 9.1 прошёл 589 шагов H.264 1080p и 357 шагов HEVC 4K HLG. Неверных кадров и промахов кэша не было. p99 от установки позиции до получения кадра из кэша составил 0,04 и 0,05 мс соответственно. Это проверка прогретого кэша на 9.1. Сравнительного замера холодных переходов с 9.0.2 нет.

## Что отслеживать в master

- **Фрагментированный MP4.** `be65e08c` учитывает только читаемые дорожки при выборе первого фрагмента после seek. Раньше дорожка глав могла заставить demux заново прочитать файл от первого фрагмента. Для отдельного видео- и аудиодемуксера FrameScrub это предметный кандидат на проверку случайных холодных переходов с замером байтов до первого правильного кадра. `a948f8e3` исправляет пропуск H.264-кадров при смене SPS и глубины переупорядочивания, что важно для теста переходов через смену формата. [MOV/fMP4](https://github.com/FFmpeg/FFmpeg/commit/be65e08c) · [H.264 POC](https://github.com/FFmpeg/FFmpeg/commit/a948f8e3)
- **Программный HEVC с несколькими слайсами без тайлов и WPP.** Патч `d2099332` включает параллельную обработку таких слайсов при slice threading. Автор измерил около 1,9× на 1080p с восемью слайсами и восьмью потоками. Ценность для FrameScrub зависит от структуры реальных файлов, ограничения потоков и задержки первого точного кадра. [HEVC slice threading](https://github.com/FFmpeg/FFmpeg/commit/d2099332)
- **Аудио после перехода.** `AVSEEK_FLAG_PREROLL` и `AVFormatContext.seek_flags` появились в master после ответвления 9.1. С флагом demux может перейти на более ранний ключевой кадр и сообщить, сколько аудиосэмплов пропустить. Это стоит оценивать по точности A/V после перехода и объёму дополнительного чтения. Точный видеокадр по-прежнему определяется по индексу и PTS после preroll. [API master](https://github.com/FFmpeg/FFmpeg/blob/7ddf7bc8a4/doc/APIchanges#L4-L44) · [AudioDecoder](../../Sources/FrameScrubCore/AudioDecoder.swift) · [VideoDecoder](../../Sources/FrameScrubCore/VideoDecoder.swift)

## Программные декодеры на новом Edge

23 ноября 2026 года, M4 Max, arm64, `master-05c674c9132e` и dav1d 1.5.5. Стенд открывает штатные AV1 1080p и HEVC Main10 4K фикстуры, выполняет `avformat_seek_file` и сбрасывает декодер перед каждым переходом. Шесть точных PTS повторяются дважды в каждом из двух прогонов с обратным порядком вариантов. Файловый кэш прогрет. Время включает демультиплексирование и программное декодирование до нужного кадра. Все PTS и контрольные суммы выбранных байтов плоскости яркости совпали. Пропускная способность измерена на двух последовательных декодированиях по 120 кадров.

| Вариант | Потоки | Seek p50 / p95, мс | Последовательное декодирование, кадров/с |
|---|---:|---:|---:|
| AV1, автоматический delay | 4 | 33,78 / 81,67 | 644–646 |
| AV1, `max_frame_delay=1` | 4 | 44,97 / 110,67 | 445–448 |
| HEVC, штатный режим | 4 | 125,38 / 287,14 | 213–214 |
| HEVC, явный frame threading | 4 | 125,89 / 284,99 | 214–215 |
| HEVC, явный slice threading | 4 | 111,26 / 262,50 | 180–195 |

AV1 с delay=1 потребовал на 1–2 пакета меньше при четырёх потоках, но декодировал медленнее. При одном потоке обе настройки дали одинаковое число пакетов и близкие времена. Для HEVC slice threading потребовал на три пакета меньше и сократил задержку при первом целевом PTS с 33,8 до 17,2 мс. У этой фикстуры включён WPP и отсутствуют тайлы. По одному файлу на кодек оставили штатный выбор потоков. Для отдельного режима быстрых переходов HEVC нужен повтор на других структурах GOP, тайлах и слайсах через реальный программный путь плеера, включая выдачу CVPixelBuffer.
