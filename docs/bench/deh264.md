# DeH264 RealPLKSR standalone experiment

2026-11-07, M4 Max, 36 GB, macOS 27.2. No app integration or new runtime dependency.
Author weights: https://github.com/Phhofm/models/releases/tag/1xDeH264_realplksr .
This is a per-image H.264 restoration model at native resolution, not a temporal model.

## Method

Apple's public FRC.mov, 3840×2160/30, re-encoded with libx264 veryfast, QP42 and QP32,
yuv420p, two threads. Compare frame90 at3s to the same frame before re-encoding.
RGB extraction uses the same FFmpeg path. The reference is already a compressed source,
not uncompressed ground truth. Crops have 64 real source pixels of context on each side.
Only one model invocation at a time; PyTorch/ORT CPU parallelism limited to two threads.

Python3.9 environment: torch2.8.0, spandrel0.4.1, coremltools9.0, onnxruntime1.19.2.
Core ML emits a warning that torch2.8 is newer than its tested2.7; output parity was checked.
Weights loaded from the author's safetensors file. For direct Core ML conversion, replace
the inference-only in-place partial channel convolution write with equivalent concatenation;
trace at64×64, convert with fixed input1×3×416×640, macOS15 MLProgram target.

## Results

Times exclude decoding, PNG output and presentation. They are short standalone tests, not
sustained playback benchmarks. The 640×416 input is a native image crop, not downscaled4K.

| Execution | Input | Cold / subsequent seconds |
|---|---|---|
| PyTorch MPS FP32 | 640×416 | 1.391 / .502, .493, .491 |
| Direct Core ML FP32, ALL | 640×416 | .963 / .444, .446 |
| Direct Core ML FP32, CPU+GPU | 640×416 | .544 / .444, .449 |
| Direct Core ML FP32, CPU+NE | 640×416 | 3.144 / 3.116, 3.119 |
| Direct Core ML FP16, ALL | 640×416 | 1.279 / .745, .665 |
| PyTorch MPS FP32, sequential tiles | 3840×2160 | 27.991, one complete frame |

The full-frame pass uses40 tiles with512-pixel cores and64-pixel context, clipped at image
edges; one tile in flight. Group normalization depends on the spatial contents of the tile,
so this is not equivalent to one monolithic4K invocation. Neither tile size nor precision
was exhaustively tuned. No claim that these results bound all possible optimized backends.

The original ONNX export through ORT/CoreML partitions into85 subgraphs and leaves unsupported
operations on CPU. First crop9.55s, second92.96s; stopped the remaining repeat. This route was
rejected. Direct Core ML avoids that overhead but remains far outside the30fps frame budget.
CPU+NE is an allowed-device configuration, not evidence of actual ANE placement.

Direct Core ML FP32 and Metal FP32 crop outputs match to RGB8 MAE .000049/255, P99=0.
FP16 versus FP32 RGB8 MAE .0861/255, P99=1; FP16 did not improve timing in this test.

## Quality and decision

The model visibly suppresses block boundaries, but adds artificial fine texture and changes
face, hair and fur detail. It does not reconstruct the reference. Four matched native384×256
crops (face/fur atQP42/QP32) all have lower RGB PSNR after processing: 28.84→27.31,
27.68→26.89,33.68→30.91,32.67→31.46dB. PSNR is not a perceptual-quality score; it is evidence
against claiming faithful detail recovery for these samples. Temporal stability was not tested.

Not suitable for real-time4K in the tested forms, and28s/frame is also impractical as normal
paused-frame refinement. Do not add it to FrameScrub on these results. The ready-made CPU
deblock benchmark remains in deblock-candidates.md; it is much faster but visually weaker.

Models, scripts, exact environment, full output and reference/DeH264/FFmpeg comparison PNGs
are stored outside the repository in the external research workspace.
